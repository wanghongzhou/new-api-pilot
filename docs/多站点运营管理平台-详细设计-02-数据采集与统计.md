## 7. 采集调度

### 7.1 周期任务

| 任务 | 周期 | 说明 |
|---|---|---|
| 在线探活 | 60 秒 | 更新在线状态、版本、汇率、数据导出开关 |
| RPM/TPM | 60 秒 | 仅保存当前值，不做历史快照 |
| 实例资源 | 60 秒 | 保存实例分钟级数据并评估资源告警 |
| 运营数据同步 | 默认 5 分钟 | 性能、充值、兑换码和上游异步任务；与实时资源监控解耦，避免逐模型与全分页请求持续占满上游额度 |
| 目录数据同步 | 默认 10 分钟 | 模型、订阅计划、定价和 system-task 目录；目录类全量快照不再按分钟重复拉取 |
| 用户属性同步 | 每小时 | 按站点分页批量同步纳管账户属性 |
| 通道同步 | 每小时 | 同步通道 ID 和名称 |
| 小时用量 | 默认每小时 H+5 | 按 usage_delay_minutes 拉取上一个完整小时；生产认证画像不超过 5 分钟 |
| 次日校验 | 每日 02:00 | 重新校验前一天落在各站统计范围内的全部 expected 小时；普通完整日为 24 小时 |
| 日终校验 | 每日一次并持续补偿 | 只校验 `verified_at` 未达到所属自然日结束时间的精确小时 |
| 分钟数据清理 | 每日一次 | 清理超过留存期的分钟资源数据 |

`POST /api/sites` 只创建本地 `unauthorized` 站点，地址 preflight 只执行不带 Token 的同步公开探测；两者都不得创建后台任务。首次授权或能力复检只有在 required capability ready 时创建 `usage_backfill`，授权事务提交后另行执行一次 immediate `site_probe`；其他授权后即时目录同步要求由其专项决策验收，不由 D140 改写。enable 创建恢复 `usage_backfill`，并把 `site_probe/realtime_stat/resource_snapshot` 作为可追踪的 durable recovery run 立即恢复当前状态，不能把 fast 正常周期历史与这些恢复任务混为一类。

除 `site_probe` 外，所有远端站点任务都要求 active、authorized、无 statistics_end_at 且站点不是 offline；具体 handler 仍必须复核 capability 与 config fence。`data_export_enabled=true` 只额外约束 `usage_hour/usage_backfill/usage_validation` 三个窗口任务，不能误用于阻止不依赖 quota_data 的安全目录采集。站点变为 offline 后只保留 probe；每次成功的周期 probe 都必须先依据从 statistics_start_at 连续排列的 complete `collection_window` 纠正 usage 游标，再从 `coalesce(last_complete_hour+3600, statistics_start_at)` 到实际墙钟的最近已闭合整点执行 missing-only 缺口对账。创建端扣除活动 validation/backfill 范围，并在同一事务内排除 complete/unavailable 小时，只为 absent/missing 小时创建连续 run，重复 probe 不得重复或创建物化后必为空的任务。offline→online 状态转换与本轮新建恢复任务必须原子提交；只有确实新建至少一个恢复 run 时才把统计状态置为 backfilling。若无可采缺口但历史状态仍为 backfilling，则按全部活动 usage_backfill 与权威目标小时重新收敛为 ready/partial；若 validation/backfill 暂时完全覆盖缺口，则保持当前活动状态并由后续成功 probe 在覆盖任务终态后继续对账。快速任务和周期任务同时从当前周期继续，不能等待次日 02:00 validation 才修复当天缺口。

### 7.2 默认并发

| 任务 | 并发上限 |
|---|---:|
| 在线探活 | 20 |
| RPM/TPM | 10 |
| 实例资源 | 10 |
| 用户/通道元数据同步 | 5 |
| 小时用量 | 5 |
| 历史回填 | 2 |

- 各站点随机错峰；
- 同一站点、同一任务类型使用进程内锁；
- 前一轮未完成时不重复启动；
- 手动补采进入同一任务队列；
- 并发数可由 admin 配置；
- 持久化任务使用 active_key 幂等约束，防止调度、手动操作和重启恢复重复入队；创建端必须使用数据库原生的无错误冲突忽略语义，冲突后读取并校验既有活跃任务，不能把预期幂等命中实现为会被 ORM 记录成 SQL error 的重复键异常。
- 站点状态、能力项和配置栅栏的数据库事务必须按完整事务边界处理 MySQL deadlock/lock-wait-timeout：仅对 1213/1205 做小次数有界重放，重放前由数据库完成整笔回滚，超过上限或上下文取消后原样返回错误；不得只重试失败的单条 capability SQL。

### 7.3 重试策略

- 在线探活失败：等待下一周期，不立即重试；
- 资源和 RPM/TPM 失败：等待下一周期；
- 用户/通道同步失败：整轮不提交，等待下一小时；
- 小时用量失败：1 分钟、5 分钟、15 分钟重试；
- 历史回填失败：失败窗口重新入队，不阻塞其他站点；
- 401：立即标记授权过期，不继续重试；
- 429：遵循 Retry-After；
- 5xx 或网络错误：按对应任务规则重试；
- 上游地址安全策略拒绝（`UPSTREAM_ADDRESS_FORBIDDEN`，包括 `cidr_mismatch`、`host_suffix_mismatch`、`special_use_address` 等确定性原因）属于配置/安全边界错误，必须终止当前窗口并标记不可重试；不得因为底层请求状态码为 0 而被统一逻辑重新标记为可重试，也不得产生零延迟重试风暴。修复配置后由新的显式重试或后续补采任务重新领取；历史 `pending`/`failed`/`missing` 状态不因配置变更自动改写。
- `upstream.allowed_cidrs`、主机后缀、超时和限流设置由运行时快照热更新；设置写入成功后当前实例立即发布，新实例通过每秒轮询在最多 2 秒内收敛。客户端不得把旧网络策略永久缓存为跨配置版本的状态；已创建客户端若继续存活，必须在下一次请求前使用最新运行时策略，或由调用方重新创建客户端。
- 站点离线后暂停除 `site_probe` 外的全部远端站点任务，仅保留在线探活；
- 站点恢复后从游标补齐所有缺失小时；offline→online 状态转换必须立即执行一次原子缺口对账，且站点保持 online 后的每次成功周期 probe 仍继续幂等对账。若同 family 已有活动 validation/backfill，则按未覆盖区间拆分创建；若本轮完全被覆盖则等待后续 probe 在覆盖任务终态后重试，不能因活动任务重叠、失败、进程重启、已经在线或重复 probe 遗漏任何缺口。恢复范围上界必须取实际墙钟最近已闭合整点，不能使用为保证数据库更新时间单调而前推的提交时间包含尚未闭合小时。

## 8. 历史回填与数据完整性

### 8.1 首次站点回填

1. 使用 `/api/user/self` 完成授权身份校验；
2. 精确读取候选 root，校验 role=100、status=1、0<created_at<=当前时间；
3. 完整分页读取远端用户快照，校验分页一致性、候选 root 为最小正 ID 且 created_at 不晚于任一用户；读取失败、空快照或证明失败时接入失败；
4. 将已验证 Token、root_created_at 和 `statistics_start_at=floorToBeijingHour(root.created_at)` 原子保存，不提供人工确认或修改入口；
5. 检查 enable_data_export=true 及必要接口能力；
6. 从起点到上一个完整小时分段拉取全部可用历史；
7. 每个历史小时同时拉取 /api/data/flow 与 /api/data 并比较 request_count、quota、token_used；
8. 两个接口一致后按站点小时窗口写入基础事实，不一致时保留旧值或空窗口并标记 missing；
9. 生成站点、全局、模型、通道历史汇总；
10. 同一站点配置下任一 `usage_backfill`（包括不同 request 的并发恢复批次）仍为 pending/running 时都必须保持 backfilling；全部活动回填终态后，以该配置所有 backfill run-window 的目标小时与 `collection_window` 对照，目标小时缺行或非 complete，以及统计范围内显式 missing/unavailable，均判为 partial。后续 retry 真正把旧目标小时修成 complete 后允许恢复 ready；request 边界、任务完成顺序以及“失败时尚未生成 collection_window”都不得掩盖未修复缺口。列表和详情只能展示该持久状态，禁止再用单个最新 run 的终态覆盖站点状态；单个 run 仅用于进度摘要。

statistics_start_at 之前属于平台明确排除的统计范围，不进入完整率分母。起点首次写入后不可修改；重新授权必须重复完整分页、软删除、最小正 ID 与最早 created_at 的首用户证明，并核对 root_user_id/root_created_at 原值，不覆盖历史边界。发现不一致时标记 SITE_INCOMPATIBLE 并要求人工排查站点身份，不自动清理历史。

### 8.2 首次账户回填

1. 创建平台纳管账户；
2. 使用 site_id + remote_user_id 从基础事实中查找全部历史；
3. 生成账户 hourly/daily；
4. 重算所属客户 hourly/daily；
5. 若基础事实存在缺口，先执行站点补采；
6. 账户回填不按账户调用任何远端统计接口，只读取本地基础事实。

### 8.3 回填期间展示

- 新建操作立即返回；
- 对象状态显示 backfilling；
- 展示回填进度、已完成范围和最近错误；
- 首次站点历史回填和新账户首次回填按完成窗口逐步可见，已回填数据允许查询，API 和页面明确标记为部分数据；
- 账户 restore 与客户 enable 采用原子开放：恢复区间在全部本地重建成功前继续返回 paused/null，只展示暂停前历史、已完成范围和进度；全部成功后一次性清除暂停边界并开放整个恢复区间，失败不暴露半套归属统计；
- Dashboard 展示全局数据完整率；
- 回填完成后自动转为 ready；
- 失败自动重试，并允许 admin 手动重试；
- 不提供取消回填。

### 8.4 采集游标与任务记录

collection_cursor 保存：

- site_id；
- cursor_key，首期固定 usage；
- last_complete_hour；
- updated_at。

collection_cursor 只用于站点级连续小时事实，usage_hour 与 usage_backfill 共享同一 `cursor_key=usage`；usage_validation 只能回退该游标，并在缺口修复后按连续 complete 重新推进。账户和客户的本地历史重建进度记录在 collection_run，不使用独立游标。

周期性 probe/realtime/resource 的成功 tick 不逐次写 collection_run，只更新当前表、Prometheus 指标和结构化日志，并把最近执行结果写入 Redis 有界历史；失败导致状态变化时仍写一条 MySQL 诊断 run。手动刷新、全部窗口任务、本地重建和导出始终持久化。Redis 历史按站点与任务类型保留最近 N 条并设置 TTL，只用于运营排查，不参与恢复、告警状态机或业务统计；Redis 写入失败不得把已完成的快速任务改判失败。这样保留故障恢复所需证据，同时避免每年近亿条无业务价值成功 tick。

快速历史查询固定为 `GET /api/fast-tasks`，必须提供 `site_id` 和 `task_type=site_probe|realtime_stat|resource_snapshot`，可选 `status=success|failed`，使用 `offset/limit` 分页。返回 `items/offset/limit/total/has_more`，其中 `site_id` 为十进制字符串。Redis 不可用时接口返回统一内部错误，`readyz` 同时报告 `redis` 未就绪。

collection_run 保存：

- site_id；
- task_type；
- start_timestamp；
- end_timestamp；
- status；
- fetched_rows；
- written_rows；
- retry_count；
- priority；
- next_attempt_at；
- heartbeat_at；
- total_windows、completed_windows、failed_windows；
- created_request_id、last_request_id；
- error_code、error_params 和仅供技术详情的 error_message；
- started_at；
- finished_at。

一个 collection_run 表示一个逻辑任务范围，可以覆盖一个或多个小时；每个 run 对每小时的执行状态、尝试次数和下次重试由不可变归属的 collection_run_window 保存。collection_window 只表达事实当前是 pending/complete/missing/unavailable，不能兼任任务进度；因此 validation 可在不隐藏既有 complete 事实的情况下进入 pending/running。Worker 每次最多处理 24 个 run window 或运行 30 秒后主动让出并重新排队，使实时小时任务能够抢占长历史回填。页面回填进度和旧任务详情以 collection_run_window 为准，事实可见性以 collection_window 为准。

### 8.5 数据完整状态

| 状态 | 含义 |
|---|---|
| complete | 采集成功，数据完整 |
| partial | 聚合范围内仅部分站点或部分窗口完整，可展示已知合计但必须标记不完整 |
| pending | 窗口尚未完成或正在采集 |
| missing | 应采集但失败，数据未知 |
| unavailable | 上游无法提供该历史区间 |
| paused | 站点、客户或账户处于暂停统计状态 |
| backfilling | 正在历史回填 |

只有 complete 且基础事实无记录时才能补 0。missing、unavailable、pending 不得显示为零流量。跨站聚合存在部分完整数据时返回已知合计并标记 partial；若没有任何完整来源则数值返回 null。

统计接口返回：

- complete_site_count；
- expected_site_count；
- unit_type、complete_unit_count、expected_unit_count；
- completeness_rate；
- missing_site_ids；
- missing_ranges。

完整率公式：站点/全局/模型/通道单桶为 complete expected site 数 / expected site 数，跨多桶为 `complete_expected_site_hours / expected_site_hours`；账户为 `complete_expected_hours / expected_hours`，起点取 remote_created_at；客户为存在至少一个 expected 账户的 `complete_customer_site_hours / expected_customer_site_hours`。分母为 0 时 completeness_rate=1、data_status=complete，但数值是否为 0 仍按具体业务对象是否存在 expected 范围判断。paused、missing、pending、unavailable 均计入分母但不计入 complete 分子；statistics_end_at 之后不进分母。

summary 的 complete_site_count/expected_site_count 表示 as_of 所在最后一个时间桶的站点数，范围完整率必须使用 unit_count 字段，不能用 distinct site 数替代 site-hour 比例。

### 8.6 稀疏存储

- 无流量小时不写事实和汇总记录；
- 全天无流量不写 daily；
- 查询趋势时由后端补齐连续时间轴；
- complete 的缺失记录补 0；
- missing 或 unavailable 返回 null 及对应状态；
- 今日摘要必须精确查询今天，不能使用最近一条 daily 冒充今日。

## 9. 唯一事实源与窗口替换

### 9.1 基础小时事实粒度

usage_fact_hourly 唯一键：

~~~text
(site_id, remote_user_id, model_name, channel_id, use_group, token_id, node_name, hour_ts)
~~~

P0-A 上游契约固定参考 `new-api` commit `7c28993f6bd9e92616f3f578212577f8b7c40b45` 的 `model/usedata.go` 与 `model/usedata_flow.go`。`/api/data/flow` 的 `use_group`、`token_id`、`token_name`、`node_name` 与用户、模型、通道同属不可丢弃的原始统计身份。token_name 是 token_id 的展示快照，不参与唯一键；同一唯一键出现多个非空名称时使用确定性的字节序最小值，保证返回顺序变化不改变 canonical hash。

上游缺失可选字段时规范化为 use_group/node_name/token_name 空字符串、token_id=0，分别表示未知分组、未知节点和未知/已删除 Token。相同站点与小时只有八维唯一键完全相同的行才能求和；不得再跨 use_group/token_id/node_name 合并。

基础事实只保存远端身份，不保存 account_id 或 customer_id。

### 9.2 小时窗口整体替换

补采或重拉不能只 upsert 返回行，必须以站点小时为单位整体替换：

1. 拉取站点完整小时数据；
2. 按包含 group/token/node 的事实唯一键聚合并计算 `usage-fact-hourly-v2` canonical hash；
3. 开启 MySQL 事务；
4. 删除 site_id + hour_ts 的旧事实；
5. 插入本次完整结果；
6. 重算受影响的六级 hourly；
7. 重算受影响日期的基础 daily 和六级 daily；
8. 提交事务；
9. collection_run 标记 success。

成功返回空数组表示真实零流量，应删除旧窗口数据。请求失败时不得删除旧数据。

`collection_window.status=complete` 不是孤立的任务状态，而是对持久化事实的可验证声明。窗口必须同时保存规范化后实际落库的 `fact_rows`；`fetched_rows` 仅表示上游原始返回行数，不能代替事实行数。complete 窗口在任何读取、复核、恢复或运维校验中都必须满足：

1. `COUNT(usage_fact_hourly WHERE site_id/hour_ts)=collection_window.fact_rows`；
2. 按 `usage-fact-hourly-v2` 相同字段、排序和编码对当前持久化事实重算的哈希等于 `collection_window.source_hash`；
3. `fact_rows=0` 且持久化事实为空时才表示真实零流量；不能仅凭“没有事实行”推断为零流量；
4. 任一条件不成立时不得继续把窗口、完整率或 daily 标为 complete/final。行数证明不一致必须立即以 `fact_proof_mismatch` 进入 `validation_failed` 告警并创建精确小时复核；复核已取得完整上游响应时，应只对该精确小时原子重写事实并重建受影响汇总；尚未取得权威响应时，应把窗口隔离为 missing、回退游标并保持可恢复告警。

哈希相同的零写优化必须同时比较“上游 canonical hash、窗口 source_hash、窗口 fact_rows、实际事实行数、实际事实哈希”五项。只比较窗口元数据会在事实被误删、恢复不完整或历史版本缺陷后永久跳过自愈，禁止采用。

### 9.3 唯一事实源

usage_fact_hourly 是统计系统唯一事实源，但只有对应 collection_window.status=complete 且 `fact_rows/事实哈希` 校验成立的事实允许进入查询和汇总。校验失败时旧事实可以保留用于比较和恢复，但必须被完整性状态隔离，不能继续计入任何可见统计：

~~~text
usage_fact_hourly
    ├─ usage_fact_daily
    ├─ account_stat_hourly / daily
    ├─ customer_stat_hourly / daily
    ├─ site_stat_hourly / daily
    ├─ global_stat_hourly / daily
    ├─ model_stat_hourly / daily
    └─ channel_stat_hourly / daily
~~~

所有汇总采用重新聚合覆盖，不使用“旧值 + 增量”更新。任何汇总表都必须能够从 `usage_fact_hourly JOIN collection_window(status=complete)` 重建。窗口由 complete 退回 missing/unavailable 时，必须同步删除或重建该窗口汇总、重建受影响 daily/global，并把 collection_cursor 回退到缺口之前的最高连续 complete 小时。

完整率、`data_status`、`is_final` 和告警必须共享上述事实完整性判定，不能由四套彼此独立的近似条件推导。定期 validation 既负责核对上游是否修订历史，也负责核对本地 complete 声明是否仍有事实支撑；发现本地事实丢失时即使上游 hash 与窗口旧 hash 相同，也必须触发精准小时修复而不是只刷新 `verified_at`。

## 10. 时间粒度与聚合规则

### 10.1 hourly

- 保存一个完整自然小时的增量；
- 有流量才写；
- 重拉后整体覆盖；
- hour_ts 为北京时间自然小时对应的 Unix 秒。
- statistics_start_at、statistics_end_at、手动补采边界和小时查询边界均必须对齐该整点；非整点请求返回 VALIDATION_ERROR，不做静默取整。

### 10.2 daily

- 当天每完成一个小时采集后立即重算；
- 表示截至最近完整小时的当日累计；
- 前端显示“截至 HH:00”；
- 次日 02:00 重新拉取并校验前一天全部数据；
- 校验完成后 is_final=true；
- 校验失败保持 is_final=false 并自动重试；
- 已结束自然日在北京时间 02:00 宽限期后仍存在未复核小时，即使尚无明确失败 run-window，也必须按未复核小时触发 `validation_failed` 告警；告警随补偿复核任务创建而保留，直至对应小时获得满足日终门槛的 `verified_at` 后自动关闭；
- 调度器不得用“最近 7 天”或非 final 日期整段重拉。它必须直接从 `collection_window` 精确选择 `status=complete AND ((verified_at IS NULL OR verified_at < date_end) OR fact_rows <> 实际事实行数)` 或带明确 mismatch 证据、且已超过次日 02:00 宽限期的小时，只为这些小时创建 `usage_validation`；相邻小时可合并为一个父 run，不连续范围可拆为同一批次的多个父 run，但 run-window 集合不得包含证明完整且已经复核的小时。历史积压按站点分批串行收敛：存在本批任一 pending/running 的历史复核 run 时不得继续预创建更老批次；无活动复核时每次合计最多选择 6 个精确小时，本批全部终态后由分钟级调度自动补充下一批，不依赖进程重启或等待下一自然日。活动范围继续由窗口任务的重叠扣除保证幂等；
- 人工补采可重新打开并重算历史日期。

### 10.3 month 和 year

- 不单独建月表和年表；
- 请求数、quota、Token 从 daily SUM；
- 活跃账户从保留远端身份的 usage_fact_hourly/daily 重新去重；
- 月、年结果按查询实时生成。

### 10.4 页面查询限制

| 粒度 | 单次最大范围 |
|---|---:|
| 小时 | 31 天 |
| 日 | 2 年 |
| 月 | 20 年 |
| 年 | 全部历史 |

超过范围时提示切换到更粗粒度。Excel、CSV 导出不受页面范围限制。

所有统计 API 的 start_timestamp/end_timestamp 必须与 granularity 的北京时间桶边界对齐；hour 对齐整点，day 对齐 00:00，month 对齐月初，year 对齐 1 月 1 日。后端拒绝未对齐范围，前端日期选择器负责生成规范边界。

### 10.5 可加指标

- request_count；
- quota；
- token_used。

上述指标可以在同一统计口径内 SUM。

### 10.6 活跃账户去重

| 层级 | 计算方式 |
|---|---|
| 账户 | 有事实记录即活跃，不单独保存 active_accounts |
| 客户 | COUNT DISTINCT account_id |
| 站点 | COUNT DISTINCT remote_user_id |
| 模型 | 单站内 COUNT DISTINCT remote_user_id |
| 通道 | 单站内 COUNT DISTINCT remote_user_id |
| 全局 | COUNT DISTINCT site_id + remote_user_id |

账户统计仍对外返回 `active_users`，但不在 account_stat 表物化：查询范围内存在账户事实时返回 `1`，expected 范围全部 complete 且无事实时返回 `0`，expected 范围不完整时返回 `null`。这三个值来自事实和完整性联合派生，不能把“不保存字段”解释为“不适用”。

活跃数不能跨小时或跨天直接 SUM。日、月、年和任意区间都必须在相应范围重新去重。

# P0-B：上游日志明细采集边界

平台按站点采集官方 new-api `GET /api/log/` 管理员日志。固定参考基线为 `new-api` commit `7c28993f6bd9e92616f3f578212577f8b7c40b45`；该接口可用性依赖站点授权、管理员权限和上游 `log.consume_enabled` 开关。不可用、未授权或开关关闭时不伪造空日志，返回明确的 `unavailable`/`disabled` 完整性状态。

采集使用有限重叠时间窗口和 `p/page_size` 安全分页：每个窗口至少保留一个稳定重叠区间，按 `(created_at, upstream_log_id)` 去重；不得把 ClickHouse 展示 ID 当游标。请求带 request ID 和固定超时，窗口提交前后校验 site `config_version`，旧配置响应丢弃。正常轮只读取最近 2 小时；历史回填或断档恢复每轮最多处理 4 个 24 小时窗口、每窗口最多 10000 行，未完成部分由后续调度继续收敛，禁止在单轮任务中遍历完整保留期。日志不是财务事实，不参与 quota/request 汇总。

日志明细保留 `type/time/user/model/token/channel/group/request_id/upstream_request_id` 筛选维度。消费日志还必须从上游 `other` 中白名单提取 `frt` 与 `stream_status.status/end_reason/error_count`：`frt` 规范化为可空的非负毫秒整数，流状态仅保存有限诊断字段，完整 `other`、`admin_info`、错误原文和任意扩展 JSON 均不得落库。IP 默认不保存；content 仅保存脱敏后的受限摘要，移除 token、password、webhook、authorization、cookie、密钥和疑似凭据，禁止保存站点访问 Token。日志 TTL 由 `logs.retention_days` 配置控制，清理只删除日志事实，不影响 hourly/daily 财务事实和 collection run 审计。
# P0-C：全站用户库存

固定官方基线为 `new-api` commit `7c28993f6bd9e92616f3f578212577f8b7c40b45`，使用管理员 `GET /api/user/?p=&page_size=` 完整分页。平台只读取并保存 id、username、display_name、role、status、group、quota、used_quota、request_count、created_at、last_login_at 和 DeletedAt；email、password、access_token、OAuth/社交绑定、setting、邀请码和支付标识不得落库或进入日志/导出。

`user_sync` 一次成功快照同时更新全站库存和已纳管 account 交集，二者在同一 site/config_version 事务提交。分页失败、total/页大小漂移、重复 ID、超过 100000 用户、非法 bigint/字符串或 config fence 均整轮失败，不写部分库存、不增加 missing。完整轮中未出现的旧用户标记 missing，上游 DeletedAt 有效的用户标记 deleted；created_at 不同的相同 remote_user_id 标记 identity_mismatch，并与 account 暂停归属逻辑一致。

当前库存保留用户级余额、累计用量和最后登录；每小时固化按 site/role/status/group 的用户数、新增用户数、近期登录用户数、quota/used_quota/request_count，用于余额、增长和活跃趋势。库存统计不替代 usage_fact 财务事实。

用户库存提交必须按远端 ID 做差集：仅新增或字段实际变化的用户进入 upsert，未变化行不得重复写入；完整快照缺失集使用单条批量状态更新推进 missing_count，identity_mismatch 行保持不可逆保护。小时事实仍按整点重建，不改变完整快照语义。
# P0-D 渠道运营快照与统计契约

渠道采集固定对接官方仓库提交 `7c28993f6bd9e92616f3f578212577f8b7c40b45` 的管理员接口 `GET /api/channel/?p=&page_size=&id_sort=true`。上游没有更新时间游标或删除 tombstone，采集器必须完整分页；`id_sort=true` 固定使用唯一 ID 倒序，禁止采用默认的非唯一 priority 排序跨页，避免同优先级渠道在分页期间重复或遗漏。平台只接收 `id/name/type/status/test_time/response_time/balance/balance_updated_time/models/group/used_quota/priority/weight/auto_ban/tag`。上游虽然可能返回 `key`、多 Key 状态、请求头覆盖、模型映射和其他私密配置，平台解码结构中不得声明这些字段，更不得读取、记录、持久化或导出。

一次成功 `channel_sync` 在同一配置版本栅栏事务中替换站点当前渠道快照并写入小时历史。当前表以 `(site_id, remote_channel_id)` 唯一；本次缺席的旧渠道标记 `missing` 并保留最后安全快照和历史，不物理删除。分页 total 漂移、重复 ID、任一非法字段、超限、超时或配置版本变化均使整个快照失败且不得部分提交。

# P0-E 性能指标历史与官方能力边界

官方基线固定为 new-api 提交 `7c28993f6bd9e92616f3f578212577f8b7c40b45`。标准接口 `GET /api/perf-metrics/summary?hours=` 用于枚举 model；`GET /api/perf-metrics?model=&group=&hours=` 返回 `model_name/series_schema/groups`，group 与 series 仅包含 `avg_ttft_ms/avg_latency_ms/success_rate/avg_tps` 和 bucket `ts`。官方内部数据库虽保存 request/success/latency_sum/ttft_sum+count/output_tokens/generation_ms counters，但标准 HTTP DTO 不暴露这些分子分母。

现有 `/api/sites/:id/performance` 继续实时代理 `/summary` 并使用 config_version 隔离的进程缓存；它不是历史事实，不参与历史聚合、导出或完整性判断。

## F1.1 采集效率与增量边界

采集实现必须优先使用上游提供的增量边界（更新时间、递增远端 ID、游标或未完成任务集合），不得在周期任务中重复拉取和重写没有变化的历史数据。只有上游契约无法提供可靠增量边界、且完整性要求明确需要全量快照时，才允许完整分页；完整快照必须在单轮成功校验后以批量、幂等方式提交。

所有同步写入必须满足以下不变量：

- 不得通过“先把站点全部行标记 missing，再逐行恢复”的方式制造全表写放大；缺失状态只能针对本轮已确认的完整快照差集更新。
- 相同远端版本或 source hash 的记录只更新必要的观测时间字段；业务字段未变化时不得执行无效整行更新。
- 逐行 upsert 只允许作为无批量替代方案；存在唯一键的事实表必须优先使用批量 upsert 或受控批量更新。
- 性能、目录、用户、渠道和任务采集必须记录请求数量、分页数量、变更行数和写入耗时，确保任务总耗时能够区分上游读取、锁等待和本地写入。
- 增量采集不能降低完整性语义：首次接入、游标丢失、版本回退、检测到缺口或上游总数漂移时，必须进入显式回填/重建路径，而不是把不完整增量当作完整成功。
- 上游管理员 API 未统一提供 `ETag`/`since`/cursor；客户端只允许对无副作用且慢变的 `status` 以外目录接口（`/api/option/`、`/api/group/`、`/api/pricing`、订阅计划）做带凭据隔离的短 TTL 请求合并/缓存。用户、财务、任务、日志、用量、性能、实例和 system-task 状态接口不得使用跨轮长缓存，以免绕过配置 fence、DNS/权限校验或完整性判断。
- 索引新增必须以实际 `EXPLAIN` 和写入代价为依据。采集事实表已有 site-leading 唯一键及时间/状态复合索引时，不得为覆盖单个低频读路径盲目堆叠二级索引；避免用索引写放大抵消增量采集收益。

基线固定为官方提交 `7c28993f6bd9e92616f3f578212577f8b7c40b45` 的管理员接口：充值使用 `GET /api/user/topup`，兑换码使用 `GET /api/redemption/` 和只读详情 `GET /api/redemption/:id`。首次、每 24 小时校准和异常回退按完整分页快照采集。其他轮次中，充值从第一页按 ID 倒序读取到同时覆盖已知最大 ID 与本地最老 `pending` 订单；兑换码读取到已知最大 ID 重叠页，并对本地全部 `enabled` ID 做精确详情复核。分页路径要求首尾 `total/max_id` fence 一致，重复 ID、空中间页、总数漂移、超过 100000 行或响应体上限均整轮失败且零部分提交。

上游没有更新时间游标、状态筛选或删除 tombstone，最大 ID 只能作为“发现新增记录”的短周期水位，不能证明旧记录没有原地变化或删除。Pilot 因而采用有界最终一致的混合策略：充值通过最老 `pending` 下界在每轮收敛待支付订单的原地状态变化；兑换码通过逐项详情在每轮收敛本地 `enabled` 记录的禁用、使用和过期字段变化。兑换详情返回 HTTP 错误、`success=false`、响应 ID 不一致或结构不合法时，不能根据错误文案猜测单行 missing，必须复用已取得的第一页退回完整分页校准。总数下降、水位丢失、配置版本变化或无法找到水位同样立即退回完整校准。增量轮次只允许 upsert 实际得到可靠事实的 ID，禁止推进 missing；只有完整校准允许按完整集合推进 missing，并把 `last_full_success_at` 前移。`complete/as_of` 只由最近完整校准证明，普通增量成功不得顺延该证明；两种轮次均按远端 ID 与业务字段做差集，正常且未变化的事实行零写，整轮新鲜度只写 collection state，不得为了刷新 `last_seen_at/collected_at` 重写快照内全部事实行。删除以及已终态历史记录的罕见原地变化仍由最多 24 小时一次的完整校准收敛，不得把增量成功宣称为强实时全量完整。

`trade_no` 与兑换码 `key` 属于禁止数据：不得声明于持久化模型、平台 DTO、日志、API、导出、fixture 或错误参数，不得通过 hash/encryption 变相保存。所有 ID/quota/amount 使用 int64，JSON 暴露为十进制字符串；money 使用严格 raw-number 解析后保存规范 decimal 文本。

# D139 system-task 只读监控采集边界

固定官方基线为 `new-api` commit `7c28993f6bd9e92616f3f578212577f8b7c40b45`，并兼容当前 `v1.0.0-rc.21` 的 `log_detail_cleanup` 系统任务。每站点仅以 root 身份读取 `GET /api/system-task/list?limit=100` 和 `GET /api/system-task/current?type=`；不得读取单任务详情，不得调用 `POST /api/system-task/log-cleanup` 或任何远端任务提交、取消、重试、清理 mutation。`current` 只对 `log_cleanup`、`log_detail_cleanup`、`channel_test`、`model_update`、`midjourney_poll`、`async_task_poll` 六个白名单 type 各请求一次，用于补齐 list 未覆盖的 pending/running 任务，禁止对 list 每行逐任务查询形成 N+1。

system-task 事实以 `remote_updated_at + source_hash` 做差集；未变化任务零写且不刷新事实时间戳，轮次的新鲜度、完整性与 current 子资源状态仅由 collection state 前移。

# D140 站点列表完整率口径

站点管理列表与卡片的“数据完整率”固定表示该站点已建立的全部 `collection_window` 事实完整率，即 `status=complete` 的窗口数除以该站点窗口总数，结果限制在 0 到 1。它不得使用最近一次 `usage_backfill` 任务的完成率，也不得只取最近 24 小时；回填任务完成只代表该次任务处理完毕，不代表历史窗口事实已全部完整。`statistics_status`（站点生命周期）与 `today.data_status`（24 小时业务指标状态）可以同时展示，但进度条必须反映站点总体窗口事实，避免“部分完整 + 100%”的矛盾。没有可评估窗口时完整率为 0；成功的空回填任务不改变该值。
